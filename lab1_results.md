# CS240 Lab 1 – RISC-V Toolchain and Compilation

## Exercise 1 – Compiling and Running a C Program

### Step 1: GCD Program

I wrote a C program named `GCD.c` to calculate the greatest common divisor of two integers using the Euclidean algorithm. The values are statically defined as `a = 48` and `b = 18`.

The algorithm repeatedly calculates the remainder and updates the two variables until `b` becomes zero. The final GCD is 6.

### Step 2: Compilation

Command:

`riscv32-unknown-elf-gcc GCD.c -o GCD`

This command compiles the C source code into a RISC-V executable named `GCD`.

### Step 3: Examining the Executable with cat

Command:

`cat GCD`

The output contains unreadable characters because `GCD` is a binary executable rather than a plain-text file. It contains machine instructions and other binary data.

### Step 4: Identifying the File Type

Command:

`file GCD`

Result:

`ELF 32-bit LSB executable, UCB RISC-V, soft-float ABI, version 1 (SYSV), statically linked, with debug_info, not stripped`

This confirms that the compiled file is a 32-bit RISC-V ELF executable.

### Step 5: Examining ELF Information

Command:

`riscv32-unknown-elf-readelf -a GCD`

The command displays information about the ELF executable, including its header, sections, symbols, and other metadata.

The ELF header identifies the file as a 32-bit, little-endian RISC-V executable. The entry point is `0x100f8`.

The complete output is saved in `readelf_output.txt`.

### Step 6: Disassembling the Executable

Command:

`riscv32-unknown-elf-objdump -D GCD`

This command disassembles the executable and displays its machine instructions in Assembly form, together with instruction addresses and hexadecimal encodings.

The `main` function includes instructions such as `li`, `lw`, `sw`, `rem`, and branch instructions. The `rem` instruction is used for the remainder calculation in the Euclidean algorithm.

The complete output is saved in `objdump_output.txt`.

### Step 7: Running without Proxy Kernel

Command:

`spike --isa=rv32i GCD`

Observed result:

`Access exception occurred while loading payload GCD:`

`Memory address 0x1000 is invalid`

The executable could not be loaded successfully in this configuration without the proxy kernel environment.

### Step 8: Running with Proxy Kernel

Command:

`spike --isa=rv32i pk GCD`

Observed output:

`GCD = 6`

With the proxy kernel (`pk`), the executable ran successfully and produced the expected result.

## Exercise 2 – Assembly, Object Files, Linking, and Debugging

### Step 1: Generating Assembly Code

Command:

`riscv32-unknown-elf-gcc -S GCD.c -o GCD.S`

This command generates the Assembly source file `GCD.S`.

The Assembly code contains the instructions implementing the GCD algorithm, including `li`, `lw`, `sw`, `rem`, and `bne`.

**Comparison with objdump:**

The `GCD.S` file contains symbolic labels such as `.L2` and `.L3`, while the disassembly generated by `objdump` shows actual instruction addresses and machine-code encodings.

For example, the Assembly file contains:

`rem a5,a4,a5`

The corresponding objdump output is:

`101dc: 02f767b3 rem a5,a4,a5`

Both represent the same remainder instruction, but objdump also shows the address and encoded machine instruction.

### Step 2: Assembling the Source

Command:

`riscv32-unknown-elf-as GCD.S -o GCD.o`

The assembler generates an object file named `GCD.o`.

The `file GCD.o` command reports:

`ELF 32-bit LSB relocatable, UCB RISC-V, soft-float ABI, version 1 (SYSV), not stripped`

The object file is relocatable and is not yet a complete executable. It requires linking.

### Step 3: Linking

The object file was linked to produce `GCD_linked`.

The `file GCD_linked` command reports:

`ELF 32-bit LSB executable, UCB RISC-V, soft-float ABI, version 1 (SYSV), statically linked, with debug_info, not stripped`

This confirms that the linked output is an executable rather than a relocatable object file.

### Step 4: Running the Linked Program

Command:

`spike --isa=rv32i pk GCD_linked`

Observed output:

`GCD = 6`

The linked executable ran successfully and produced the expected result.

### Step 5: Debugging Register and Memory Changes

I used Spike's debug mode to inspect the effects of individual instructions on registers and memory.

Debug command:

`spike -d --isa=RV32IMAFDC pk GCD_linked`

The M extension is enabled because the GCD program uses the `rem` instruction.

**Observation 1 – Stack Pointer**

Instruction:

`addi sp,sp,-32`

Before execution:

`sp = 0x7ffffda0`

After execution:

`sp = 0x7ffffd80`

The instruction decreased the stack pointer by 32 bytes to reserve stack space for the function.

**Observation 2 – Memory Store**

Instruction:

`sw ra,28(sp)`

The return address register contained:

`ra = 0x00010140`

After executing the instruction, I inspected memory using:

`mem 0 0x7ffffd9c`

Observed value:

`0x00010140`

This confirms that the `sw` instruction stored the return address in stack memory.

**Observation 3 – Remainder Instruction**

Instruction:

`rem a5,a4,a5`

Before execution:

`a4 = 0x00000030` (48)

`a5 = 0x00000012` (18)

After execution:

`a5 = 0x0000000c` (12)

The instruction calculated `48 % 18 = 12` and stored the remainder in register `a5`.

These observations demonstrate how RISC-V instructions modify registers, use stack memory, and perform arithmetic operations.
